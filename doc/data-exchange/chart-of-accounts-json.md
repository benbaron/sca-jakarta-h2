# Chart of Accounts JSON contract

## 1. Purpose and authority

Chart of Accounts JSON transfers account definitions and hierarchy. It does not transfer transactions, funds as independent master data, bank statements, other company records, or an H2 database.

The compatibility input shape is frozen from actual output produced by donor commit `c697630ec1f784ebe8338d7300da6c9ac801b180`. The fixture `src/test/resources/data-exchange/coa-json/valid/donor-generated.json` is generated by the donor's `ChartOfAccountsIOService`, rather than inferred from its Javadoc.

The application MUST use DTOs for this interchange. Hibernate/JPA entities MUST NOT be serialized directly.

## 2. Format recognition and versions

Recognition is by root content, not filename.

Two input families are supported:

1. **Donor compatibility input**: an unversioned root object whose emitted account collection is `chartOfAccounts` and whose account objects use donor property names.
2. **SCA Bookkeeping output**: `"format": "SCA-COA"` and `"version": "1.0"`.

A root that matches neither family is rejected. Future `SCA-COA` versions are rejected unless explicitly added to this contract.

Writers emit only deterministic `SCA-COA` version `1.0`.

`BANK` remains a **portable compatibility type token** in SCA-COA 1.0 even though it is no longer an internal `AccountType`. A reader maps portable `BANK` to `AccountType.ASSET + AccountFunction.BANK`; the optional `subtype` independently carries `CASH` or another financial/schedule classification. A writer emits portable type `BANK` for an internal account with the `BANK` function. This preserves existing files without conflating balance-sheet class with operational banking behavior.

## 3. Actual donor compatibility shape

The governed donor fixture freezes the actual emitted root and field names. The root properties, in emitted order, are:

- `chartOfAccounts`: the donor model's full account list and the one authoritative compatibility input collection;
- `rootAccounts`: a derived duplicate containing only root accounts;
- `accountNames`: a derived comma-separated display string; and
- `accounts`: a second derived duplicate of the full account list.

The donor Javadoc advertises `_schemaVersion`, but actual output does not emit it. It also understates the derived duplicate properties. Import MUST read each account exactly once from `chartOfAccounts`. When `rootAccounts`, `accountNames`, or `accounts` are present, the importer validates that they are consistent with `chartOfAccounts`, reports compatibility warnings for the redundant shape, and never imports the duplicates as additional accounts.

Each emitted donor account contains, in order:

- `associatedFundIds`;
- `accountNumber`: source account code/number;
- `increaseSide`: donor equivalent of normal balance;
- `name`;
- `accountCode`: optional donor classification code;
- `accountType`;
- `parentAccountId`;
- `currency`;
- `openingBalance`;
- `supplementalLineKinds`; and
- `effectiveIncreaseSide`, a derived value that must agree with the explicit or type-derived increase side.

The donor model may expose other future fields. Unknown fields are retained only for warning/reporting and MUST NOT be silently applied.

Field conversion rules are:

- `accountNumber` becomes the portable account `code` unless an explicit `MAP_CODES` mapping overrides it;
- `increaseSide` maps to `normalBalance`;
- a compatible donor `accountType` maps to the current accounting type/function/subtype classification;
- donor checking, savings, bank, and cash types map internally to `AccountType.ASSET`, `AccountFunction.BANK`, and `AccountSubtype.CASH`;
- `parentAccountId` maps to `parentCode`;
- `currency` must equal the target company's currency or produce a blocking mismatch;
- `associatedFundIds` and `supplementalLineKinds` are unsupported by the current `Account` entity and produce named warnings;
- `accountCode` is retained as unsupported compatibility metadata unless a later governed field is added; and
- `effectiveIncreaseSide` is validation evidence only and is not a second persisted field.

## 4. Versioned deterministic output shape

The SCA Bookkeeping output root is:

```json
{
  "format": "SCA-COA",
  "version": "1.0",
  "chart": {
    "name": "Fictional Branch Chart",
    "chartVersion": "2026",
    "status": "DRAFT",
    "currency": "USD"
  },
  "accounts": []
}
```

Each account contains, in this order:

- `code`;
- `name`;
- `type`;
- `subtype` when present;
- `normalBalance`;
- `parentCode` when present;
- `posting`;
- `active`;
- `effectiveFrom` when present;
- `effectiveTo` when present;
- `openingBalance` as a plain decimal string; and
- `description` when present.

Output uses UTF-8 without BOM, LF endings, two-space indentation, fixed property order, and accounts ordered parent-before-child and then by code. A repeated export from unchanged chart state is byte-identical. SHA-256 of final bytes is reported.

## 5. Import modes

### 5.1 `CREATE_NEW_CHART`

Creates a new chart and accounts. The target chart name/version must not conflict with an existing chart selected for the company. All validation occurs before one atomic commit. The new chart is created as `DRAFT` and is not made active; activation remains a separate deliberate company-administration action.

### 5.2 `MERGE_BY_CODE`

Matches source `code` to target `code` in the active company chart. It may create missing accounts and update explicitly supported fields of compatible existing accounts. It MUST NOT delete, deactivate, detach, or reparent absent local accounts.

### 5.3 `MAP_CODES`

Requires an explicit source-to-target code map for every source account used. The preview displays mappings, collisions, and unmapped codes. One target account MUST NOT receive multiple source accounts unless an explicitly supported consolidation rule exists; P15-S3 initially treats that as blocking.

## 6. Validation

Preview MUST validate the complete graph before commit:

- required nonblank code and name;
- source-code uniqueness after mapping;
- target-code uniqueness within the selected chart;
- parent existence and parent-before-child ordering after normalization;
- no self-parenting or direct/indirect hierarchy cycle;
- compatible account type and subtype;
- compatible normal balance for type;
- posting-state consistency, including no posting parent that also has imported children;
- active/effective-date consistency;
- currency consistency;
- opening-balance policy;
- history restrictions for structural changes;
- duplicate JSON object keys; and
- limits in section 10.

A missing parent, duplicate code, cycle, unsupported type, incompatible normal balance, or history-destructive change is blocking. An unknown but safely ignorable field produces a warning naming the field and count.

## 7. Opening balances and history

Chart interchange does not create opening-balance transactions.

For a newly created, unused chart, an opening balance may populate the `Account.openingBalance` field after explicit confirmation. It must fit current `DECIMAL(19,2)` without rounding.

For an existing account with canonical transaction history, a different imported opening balance is a blocking financial conflict. The importer MUST NOT silently alter history or create a balancing transaction. Identical values are idempotent. Any future supported conversion to a canonical opening transaction requires a separately governed migration and user-visible accounting policy.

## 8. Idempotency and atomicity

An identical second import MUST make no account changes. Matching is by normalized source identity and selected mode, never local numeric primary key alone.

All account and hierarchy writes occur in one caller-owned JPA transaction. Parent accounts are persisted before children, and durable interchange identities are written inside the same transaction. Any late failure rolls back the chart, accounts, hierarchy, and identity records together. Preview and validation perform no writes.

Absent source accounts never delete or deactivate local accounts. A separate explicit administrative action is required for deactivation or deletion under current account-history protections.

## 9. Results and warnings

The operation result reports:

- detected family/version, source bytes, and SHA-256;
- selected chart and import mode;
- effective code mappings;
- counts read, created, updated, identical, skipped, warning, and error;
- hierarchy and history conflicts;
- opening-balance decisions; and
- committed or rolled-back state.

Export reports chart/account counts, destination, byte count, and SHA-256.

## 10. Security and limits

| Limit | Value |
|---|---:|
| File size | 16 MiB |
| JSON nesting depth | 32 |
| Account count | 100,000 |
| JSON string length | 1 MiB per value |
| JSON number length | 128 characters |
| Account code | 64 Unicode code points |
| Account name | 200 Unicode code points |
| Description | 1 MiB input; current entity limit applies on commit |

Input is strict UTF-8. A UTF-8 BOM may be stripped with a warning; UTF-16/32 and malformed sequences are rejected. Duplicate object keys are rejected.

Money is finite plain decimal, no exponent is emitted, and no silent rounding is allowed. Opening balances must fit `DECIMAL(19,2)`. Dates use valid ISO `YYYY-MM-DD` and must be within `1900-01-01` through `9999-12-31`.

Path, overwrite, temporary-file, atomic-move, and SHA-256 rules are the same as SCLX export. Malformed JSON, unsupported versions, limit violations, duplicate identifiers, missing parents, and cycles are blocking.

## 11. Separation from other exchange types

- This format does not carry `Txn`, `TxnSplit`, bank statement, asset, inventory, budget-history, or audit records.
- SCLX is the company business-data interchange and may reference a chart as part of a larger graph.
- Whole-database transfer preserves all H2 records and schema state.
- OFX/QFX/CSV carry statement activity only.

UI labels, services, DTOs, tests, and file choosers MUST retain the explicit name **Chart of Accounts JSON** and MUST NOT call it a ledger, backup, SCLX, or bank import.

## 12. P15-S3 implementation and owner verification

Merged PR #197 implements the contract through DTOs under `org.nonprofitbookkeeping.interchange.coa`, `ChartOfAccountsJsonService`, `ChartOfAccountsJsonImportService`, and the production `ChartOfAccountsInterchangePanel` wrapper. The wrapper preserves the established single-account editor and adds explicit **Import JSON…** and **Export JSON…** actions without creating a new navigation destination or generic import/export job log.

Automated coverage includes donor-fixture conversion, deterministic byte-identical export, duplicate-key rejection, hierarchy-cycle blocking, new-chart import, merge idempotency, absent-local-account retention, durable identity writes, and injected late rollback.

## P20-S3 runtime authorization

Production Chart of Accounts JSON import commits require `BOOKKEEPING_WRITE` at `ChartOfAccountsJsonImportService.commit(...)` before ordinary commit validation. The production JavaFX wrapper obtains that guarded service from `UiServiceRegistry`; JSON preview remains non-mutating. The **Import JSON…** control reflects `BOOKKEEPING_WRITE`, while **Export JSON…** reflects `EXPORT`. UI disabling is explanatory only; direct service calls remain the authoritative authorization boundary.
