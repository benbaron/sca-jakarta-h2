## Discovered gap and contract

Before this repair, repeated New Save commands before the first callback created multiple canonical receipts/obligations. An uncertain post-commit read failure can also leave a new-entry draft whose retry creates another transaction. The company lock prevents competing over-applications, but does not deduplicate collections. Repair the one existing canonical Journal path rather than create a separate NMR command/ledger.

The Journal generates one operation UUID for each deliberate New draft, keeps it through validation/write/read failures and uses it for all create retries. It does not change the UUID when the user changes a failed draft: an unaccepted operation may be corrected and retried, while changed input for an already accepted UUID must reject. New creates a distinct operation even with identical amounts. While Save is in flight, Save/New/Edit/Delete and the editable region cannot dispatch another operation or replace the saved draft. Existing File/toolbar Save has the same guarded route, permission and draft ownership.

The canonical service uses the supplied UUID as both Txn portableId and its single existing TRANSACTION_ENTERED AuditEvent portableId. The create audit reason contains a version-1 SHA-256 of normalized accounting input (company/native reference IDs, dates, header, complete ordered lines/payment facts and supplemental/NMR/merchant facts). Money normalizes at canonical four-decimal precision, optional text follows existing persistence semantics, and component link order is normalized. The original receipt/hash never changes on later edits/reversals. Existing audit and transaction unique constraints plus the company lock govern concurrency; failures roll back transaction, metadata and receipt together.

An exact authorized same-company retry returns the current retained transaction and adds no ledger, metadata or audit record, including after later closure, reconciliation or correction. This acknowledges the accepted operation and never reapplies its original data over later changes. Changed input, foreign-company reuse, incompatible identity collisions and deleted transactions reject; retained audit identity prevents resurrection. Permission is checked on every call before lookup. Old no-key service calls remain deliberate new operations and import/correction authority is unchanged. No schema or separate request persistence is introduced.

SCLX already preserves intrinsic transaction/audit UUIDs and the complete audit reason, including these receipts, with existing conflict/Keep target/retry/rollback rules. The request hash refers to the original database's native IDs; SCLX restores business facts and receipt provenance, not a promise that a source database's client request can be replayed with remapped target IDs. Such a collision rejects rather than creating another transaction. Whole-database backup/restore preserves full native retry state. No newly accepted accounting fact is omitted from interchange.
