# P27-S4 integrated portability audit

## Execution boundary

S3/S3B/S3B2 are merged in PR #392 at `76fe8450`; accepted head `e3091452` passed clean/repeat/JavaFX workflow `40428989992`. Generic accounting rules remain the adopted submission contract. This audit does not introduce an official form, policy-rate engine, internal attachments or approvals.

S4 is executed in four mergeable slices:

1. **S4A — inventory and recovery gate (this slice):** inspect the actual export/parser/preview/identity/commit authorities, record the durable field inventory and gaps, exercise real-file review/close portability and whole-database recovery, and retain existing feature-level tests.
2. **S4B — complete budget metadata:** preserve non-calendar plan dates, exact DRAFT/ACTIVE/ARCHIVED state, activation/archive times, notes and creation/update metadata, including line notes/times, through a versioned optional application extension. Existing core files remain compatible. Validate consistency with the core projection, deterministic identity/conflict/Keep target, inactive Event/Fund history, restart/retry, authorization and late rollback. Do not reconstruct dates as January–December or collapse ARCHIVED to DRAFT when full metadata is present.
3. **S4C — operational fund-transfer portability:** add a strict versioned extension through the existing snapshot, preview, identity and atomic commit paths. Restore original/reversal transaction and fund relationships, exact amounts/dates/reasons and retained native request provenance. Never post transfer accounting twice. Require deterministic output, supported-version validation, ownership/history validation, existing-company conflict/Keep target, restart/retry and late rollback tests. Source command hashes that bind native IDs remain provenance after remapping; never pretend they authorize a different target command.
4. **S4D — integrated compatibility and evidence validation gate:** validate recognized structured close-review audit payload versions/shape before commit, while preserving opaque historical source text and keeping computed findings non-authoritative. Then combine P24–P27 features in a representative fixture, compare supported operational histories and canonical report results after new-company import, exercise populated-target conflicts and unsupported versions, and compare full populated-database recovery. Split evidence hardening from the combined fixture if implementation inspection shows it needs an independent merge. S4 and P28 remain gated until all slices merge. The separate feature tests listed below are evidence of their bounded contracts, not a substitute for that fixture.

No feature is declared portable solely because a JSON key exists. Backup is a complete database copy; selected-company SCLX is a governed business-data graph with exclusions.

## Deliberate exclusions and historical provenance

| State | Selected-company SCLX | Whole database |
|---|---|---|
| Users, role assignments, password hashes, login/session state | Excluded; target access policy governs. No imported actor text authenticates a session | Stored security rows retained; an in-memory logged-in session is not a database fact |
| Company UI/table/divider/recent-file settings | Excluded; target UI configuration governs | Persisted preferences retained; unsaved drafts and open panes are not retained |
| Flyway/H2/JDBC paths, write-guard row/triggers, source-machine file paths | Excluded; target migration installs its own guard and schema | Schema, guard and trigger definitions retained/validated by migration; filesystem paths outside H2 are not copied |
| Raw external receipts, approvals/count packets and attachments | Not stored by the application; only entered references/attestations travel | Reference facts retained; referenced external files remain external |
| Other-company/global/unowned audit, compatibility ledger/open-item tables, eliminated generic-job state | Excluded from selected-company business authority | Persisted rows retained without making them current ledger authority |
| Calculated reports, readiness/preview findings as current authority | Recalculate from target canonical data. A recorded review contains historical findings only | Recalculate current projections; retained review snapshots remain historical |
| Native identifiers embedded in opaque audit before/after/reason/subject text | Preserve exact factual text; do not rewrite polymorphic text into guessed target foreign keys | Native IDs and references retained exactly |

The review UUID and range/event identities remain portable. A target can import historical close/reopen events without pretending it just passed an interactive close review. A new close still requires the current target assessment, applicable reference/reason facts, zero blockers and a matching revision. Reopening/reclosing requires a fresh review. A source backup SHA is the identity of that captured source backup, never a claim that it hashes the target database.
