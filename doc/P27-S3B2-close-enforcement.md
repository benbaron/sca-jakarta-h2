# P27-S3B2 — Atomic reviewed period close

After merged S3B1, complete factual close enforcement through PeriodCloseRangeService. No approval queue, external document verification, rate policy, attachment system, second ledger or automatic accounting entry is introduced. Self-attested evidence remains a factual external-reference record.

Inspection reuses production PeriodCloseRangeService, packet canonical projections, review audit authority and existing period protections. Donor MonthlyCloseChecklistService still uses alternate gateways/unwired close checks and supplies no compatible atomicity mechanism; no donor persistence or checklist authority is ported. V90 remains an ordinary checksummed SQL migration and calls a temporary installer alias in the existing org.nonprofitbookkeeping namespace, removing that alias immediately afterward.

V90 nondestructively installs one metadata guard row and H2 BEFORE statement triggers for every existing application base table except the guard, Flyway history and security_event (denial recording must remain independent). Statement writes acquire the same database row lock until commit/rollback, including JPA, native SQL, operational projections' sources, audit references, imports, corrections and future source changes within those tables. This deliberately uses coarse database-file serialization for correctness. New tables in later migrations must install this trigger before becoming readiness sources; a migration test inventories all application tables. The guard stores no balance, policy, actor or readiness cache. No business data or existing close history is backfilled/reclassified. Deadlocks/timeouts fail and roll back; they never bypass validation.

H2 statement triggers and cascading foreign-key operations can inherit auto-commit mode. The trigger temporarily suppresses that H2-local flag around its lock query and restores it directly without JDBC's implicit commit. It never commits or rolls back the caller's transaction. Upgrade tests cover MERGE, auto-commit cascades, rollback and unchanged connection mode; the merchant settlement migration's original cascade regression is retained.

Interactive close acquires only this guard before reading company, recorded review and canonical projections. It must not acquire a company/asset lock after the guard, avoiding inversion against commands that acquire company locks before writing. Use the exact same canonical report assembler as snapshot export, reading committed stable data through independent read EntityManagers while all source writers are excluded. Do not create a backup or claim a backup SHA for this live transaction assessment. Hold the guard through range, factual event and audit commit. Write-time PeriodCloseRangeService.requireOpen acquires the guard before querying closed ranges, so a transaction waiting behind close checks the committed close state before writing. Reopen and historical interchange range validation also hold the guard.

Require an exact-company/date recorded review (explicit supplied identity or most recent review for that exact scope), matching accounting content revision, explicit self-attestation/references, zero current blockers, and a retained nonblank reason for every current WARNING. Never accept a reason for a blocker. Canonical recomputation, not imported computed findings, owns readiness. Recheck BOOKKEEPING_WRITE/actor at commit. Read-only preview and evidence recording remain available while close is blocked.

Use the review UUID as close-range identity. Exact retry of a CLOSED range with the same company/dates/kind/reason returns the original range without another event/audit, including after restart. Conflicting reuse fails. A reopened range requires a newly recorded review before reclose; old range/reopen/event/evidence history remains unchanged. The close audit after-value retains review ID, canonical content revision and warning-reason identities. Existing SCLX period-range and generic audit extensions retain those facts; imported historical closes continue through the governed interchange seam, without replaying interactive policy or synthesizing current review approval.

The Period Close action captures service/company/dates/kind/actor/reason on the FX thread, runs guarded close asynchronously, prevents duplicate submission and reports factual rejection. Explain that a current recorded review and all warning reasons are required. Preserve existing explicit Save Closed Range/Reopen controls and Review Evidence/shared Save; no enabled action promises certification before service validation.

Authenticated session publication is volatile so worker-thread commit checks observe FX-thread logout/role replacements. This is the narrow background-authorization prerequisite; it adds no identity cache or permission policy.

Tests must upgrade populated V89 in-memory databases, preserve old business/close data, inventory trigger coverage, exercise direct operational writes blocked by the guard, and prove both writer-before-close (new content causes rejection) and close-before-financial-writer (period check rejects after close commits). Cover review/period/company mismatch, missing/stale reviews, blockers and missing warning reasons, accepted reasons, live permission/actor changes, rollback, simultaneous closes, exact retry/restart, reopen/reclose history and backup/SCLX recovery. Prior closed-period protection tests seed factual historical closes through the same interchange seam used for recovery, rather than bypassing the new interactive gate.

User checks: in a disposable company, Preview Readiness for a chosen period, correct blockers, record review references and reasons for every warning in Review Evidence, then Save Closed Range. Confirm stored close/event/audit points to that review. A source edit after review must cause a new close attempt to fail until a fresh review is recorded. Verify Viewer denial, duplicate retry without duplicate history, reopening with existing reason policy, fresh review before reclosing, and rejection of later entries dated inside the closed range. Open the packet and factual histories; review remains a self-attestation, not independently verified approval. Check laptop layout, busy controls and readable error messages. Native owner results are recorded separately.
